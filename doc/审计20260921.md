我把 `codex/mympd-integration` 分支按上一轮“**安全 + 架构 + 控制台/UI + 运维**”标准重新审了一遍，并重点检查了 myMPD 引入后是否破坏原来的安全边界。

## 结论

**这一分支整体方向是明显进步的，但目前不建议直接合并到 main。**

原因不是 myMPD 方案本身有问题——相反，**用成熟的 myMPD 接管本地曲库、队列、歌单、封面、歌词等播放器能力，比继续自研完整播放器前端更合理**。myMPD 本身就是以 MPD 为唯一数据源的移动友好 Web/PWA 客户端，具备队列、歌单、曲库搜索等完整能力。([GitHub][1])

现在真正需要解决的是一个新引入的 **P0 安全边界问题**：

> **1781 控制台已经有登录保护，但 myMPD 的 1782 又被直接暴露到整个 LAN，并且当前没有配置 myMPD PIN/ACL，因此实际上绕过了 1781 的认证。**

把这个问题和 myMPD 配置持久化问题修掉后，我认为这个分支的架构反而比上一版更适合作为长期路线。

# 二、P0：myMPD 1782 重新打开了认证绕过

这是当前分支唯一一个我认为必须在 merge 前解决的问题。

目前 Supervisor 启动 myMPD：

```text
MYMPD_HTTP=true
MYMPD_HTTP_HOST=0.0.0.0
MYMPD_HTTP_PORT=1782
MYMPD_SSL=false
```

同时没有看到对应 PIN/ACL 的初始化配置。

README 也明确把：

```text
http://<FNOS-IP>:1782
```

作为 LAN 可直接访问的 myMPD 地址。

于是当前实际边界变成：

```text
                    ┌──── 1781 ──── 登录认证 ──┐
LAN ────────────────┤                          │
                    │      Snap 控制台          │
                    │                          │
                    └──── 1782 ──── myMPD ─────┐
                                      无统一认证
```

myMPD API 本身能够直接操作播放器，例如官方 API 文档列出的：

```text
MYMPD_API_PLAYER_STATE
MYMPD_API_PLAYER_VOLUME_SET
...
```

并通过 `/api/<partition>` 和 `/ws/<partition>` 提供 JSON-RPC/WebSocket 控制。只有启用了 PIN 保护以后，需要保护的方法才会要求 `X-myMPD-Session` 会话令牌。([Jcorporation][2])

所以现在：

> 给 1781 加密码，但把未保护的 myMPD 1782 直接暴露出来，相当于安全边界只保护了“设备管理页”，没有保护真正的播放器控制面。

myMPD 还提供队列、歌单、MPD 数据库浏览等大量能力，因此 1782 的权限实际上比之前简化版控制台更大。([GitHub][3])

### 我建议的最终方案

短期可以做：

```text
1782 → myMPD PIN
+
ACL 限制可信 LAN
```

这样改动小。

但长期更推荐：

```text
LAN
 │
 ▼
1781 / HTTPS
 │
 ├── /                  Snap/Room 控制台
 │
 └── /player/           Reverse Proxy
                              │
                              ▼
                      myMPD 127.0.0.1:1782
```

最终网络应该变成：

```text
0.0.0.0
 ├─ 1704      Snapcast audio
 ├─ 1781      唯一 Web 入口
 ├─ AirPlay
 └─ DLNA

127.0.0.1 only
 ├─ 1705      Snap RPC
 ├─ 1780      Snap HTTP
 ├─ 1782      myMPD
 └─ 6600      MPD
```

这是架构上最干净的方案。

不过**不建议让现在这个 Python `ThreadingHTTPServer` 自己实现 WebSocket reverse proxy**。myMPD 使用 `/ws/<partition>` 推送通知。([Jcorporation][2])

应该加一个真正的反向代理，例如 Caddy/nginx，或者保持 myMPD 自身 PIN。

# 三、P0/P1：`#player` 可以在 1781 登录完成前加载 myMPD

这里有一个比较隐蔽的启动时序问题。

当前启动大致是：

```javascript
initTheme();
setPlayerLinks();
initEvents();
initGroups();

await checkAuth();
```

而 `initEvents()` 会根据当前 hash 导航。

所以用户直接访问：

```text
http://IP:1781/#player
```

可能形成：

```text
initEvents()
   ↓
navigate("player")
   ↓
loadPlayer()
   ↓
iframe.src = http://IP:1782/

        ↓

checkAuth()
```

也就是说 myMPD iframe 可以在 1781 完成认证之前加载。

在目前 1782 本来就未认证的情况下，它进一步证明了两个系统实际上没有共享安全边界。

建议改成：

```javascript
initTheme();
setPlayerLinks();
bindEvents();

const authenticated = await checkAuth();

if (authenticated) {
    navigate(initialRoute);
}
```

并且：

```javascript
loadPlayer()
```

本身也应该检查认证状态。

# 五、P1：myMPD 配置“首次启动持久化”会影响以后安全整改

这是 myMPD 集成里很容易踩的坑。

myMPD 官方说明：

> 默认配置文件会在**第一次启动**时生成。

之后配置就存在 working directory 中。([Jcorporation][4])

而当前：

```text
/app/data/mympd/work
/app/data/mympd/cache
```

都是持久化目录。

于是会出现：

```text
第一次安装

MYMPD_HTTP_HOST=0.0.0.0
        ↓
data/mympd/work/config...
```

以后代码改成：

```text
MYMPD_HTTP_HOST=127.0.0.1
```

**不能简单假定老用户重新启动容器就一定同步得到新的安全配置。**

PIN 更明显，因为官方配置里：

```text
pin_hash
```

本身没有直接对应环境变量，需要配置 SHA-256 PIN hash；官方建议通过 `mympd -p` 生成。([Jcorporation][5])

因此下一步千万不要只是：

```text
supervisord.conf
0.0.0.0 → 127.0.0.1
```

然后认为完成。

建议增加：

```text
mympd-init.sh
```

启动时：

```text
读取已有 myMPD 配置
        ↓
验证强制安全参数
        ↓
如果不符合
   ├─ 安全迁移
   或
   └─ fail closed + 明确报错
```

尤其要覆盖**从当前分支升级的已有 data 目录**。

# 六、P1：`/api/health` 仍然做得太“重”

当前认证逻辑里：

```text
/api/health
/api/auth
/api/login
```

属于无需登录的接口。

这本身合理。

问题是现在 `/api/health` 不是：

```json
{"ok":true}
```

这种简单 readiness probe，而是会进一步获取综合状态，其中包括 Snapserver/MPD 状态。

于是 LAN 上未认证设备可以不断：

```text
GET /api/health
GET /api/health
GET /api/health
...
```

间接制造：

```text
HTTP
 ↓
Snap RPC
 ↓
MPD query
```

这还谈不上严重漏洞，但健康检查不应该承担完整状态查询。

建议：

```text
/api/health

{
  "ok": true,
  "control": true,
  "snapserver": true,
  "mpd": true,
  "mympd": true
}
```

数据由后台缓存维护。

健康检查本身应该是 O(1) 的。

# 十、还有几个次要问题

这些不阻塞合并，可以归到 P2。

`entrypoint.sh` 目前每次启动都有：

```text
chown -R snapcast:snapcast /app/data
```

myMPD cache/database 长期增长后，每次启动递归 chown 会越来越慢；最好仅在 UID/GID 改变时处理。

AirPlay `drop-session` 脚本使用：

```text
dbus-send --system
```

但 Supervisor 中看到的是 session DBus。这里建议再做一次实际容器验证，确认快速 DropSession 路径是否真正生效，否则现在可能主要依靠 `SIGTERM shairport-sync` fallback。

CSP 里为了 iframe 放开：

```text
frame-src http://*:1782 https://*:1782
```

范围偏宽。等 1782 统一代理到同源后，可以直接收紧成：

```text
frame-src 'self'
```

另外 HTML 中还有 `192.168.2.126:1782` 的 fallback，但 JS 启动后实际上会根据：

```javascript
location.hostname
```

覆盖，所以不再是实际功能性 bug；不过最好删掉硬编码，避免 JS 加载失败时显示错误地址。

最后，播放器状态仍是 2 秒 polling；现在控制台已经很轻，这已经不值得作为优先改造项。SSE 可以以后再做。
