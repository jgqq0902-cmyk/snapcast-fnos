## 1. 结论摘要

本次基于 `3ec3f5a` 最新代码重新审计后，上一轮最重要的 P0 风险——**myMPD 1782 裸露在 LAN、可绕过 1781 登录认证**——已经关闭。

当前架构已经基本收敛为：

```text
LAN
 │
 ▼
1781 nginx
 │
 ├── /          → 127.0.0.1:1783 Control
 │
 └── /player/   → auth_request
                    ↓
                 /api/session-check
                    ↓
```

## 3. SEC-01：登录限流在 nginx 后可能退化为全局锁定

### 3.1 现状

Control 登录限流当前以：

```python
self.client_address[0]
```

作为来源地址。

但生产拓扑已经变成：

```text
LAN Client
   ↓
nginx :1781
   ↓
Control 127.0.0.1:1783
```

因此 Control 很可能把所有客户端都识别为：

```text
127.0.0.1
```

登录限流逻辑为：

```text
60 秒
最多 5 次失败
```

可能出现：

```text
客户端 A 输错 5 次
        ↓
LOGIN_ATTEMPTS["127.0.0.1"] 达限
        ↓
客户端 B / C / D 全部被一起锁 60 秒
```

### 3.2 风险

这是可用性问题，也会让认证 DoS 成本极低。

### 3.3 推荐实现

优先方案：**把 login rate limit 移到 nginx。**

建议：

```nginx
limit_req_zone $binary_remote_addr zone=login_limit:1m rate=5r/m;
```

仅对：

```text
/api/login
```

应用。

Control 内仍可保留基础保护，但不要再把 `127.0.0.1` 当独立客户端。

备选方案：

nginx 增加：

```nginx
proxy_set_header X-Real-IP $remote_addr;
```

Control 仅当 TCP peer 为 `127.0.0.1` 时才信任 `X-Real-IP`。

禁止：

- 无条件信任用户可伪造的 `X-Forwarded-For`。
- 根据任意 Header 直接生成限流 key。

### 3.4 验收

新增测试：

```text
Client A 连续失败达到限流
Client B 仍可登录

伪造 X-Real-IP / X-Forwarded-For
不得绕过真实限流策略
```

## 4. SEC-02：Web 登录仍为纯 HTTP

### 4.1 现状

nginx 当前监听普通 HTTP：

```text
1781
```

登录 cookie 已正确设置：

```text
HttpOnly
SameSite=Strict
```

但没有 `Secure`。

### 4.2 风险

在完全可信、隔离家庭 VLAN 中可以接受。

但如果网络中存在：

- IoT
- 访客设备
- 办公网
- 不可信 Wi-Fi

则登录密码及 session cookie 不具备传输层加密。

### 4.3 建议

新增可选配置：

```text
WEB_TLS_ENABLED=false
WEB_TLS_PORT=1781
TLS_CERT=/app/certs/...
TLS_KEY=/app/certs/...
```

当 HTTPS 启用：

```text
Set-Cookie:
HttpOnly;
SameSite=Strict;
Secure;
```

默认可继续允许可信 LAN 使用 HTTP，不强制在当前版本切换。

### 4.4 优先级

P1/P2，不作为当前 merge blocker。

## 7. REL-01：Group 创建缺少事务回滚

### 7.1 现状

`create_group()` 可能执行：

```text
Step 1:
从原 group 移出 anchor client

Step 2:
等待 Snapserver 自动建立新 group

Step 3:
Group.SetClients(new,...)

Step 4:
Group.SetName(...)

Step 5:
Group.SetStream(...)
```

任一步骤失败，都可能留下半完成状态。

`GROUP_MUTATION_LOCK` 只能防并发，不能回滚。

### 7.2 风险

例如：

```text
原来：
A = [c1,c2]
B = [c3]

创建：
NEW = [c1,c3]

执行到一半失败：

A = [c2]
AUTO = [c1]
B = [c3]
```

用户最终看到和操作预期不同的分组结构。

### 7.3 建议

在 mutation 前保存 snapshot：

```python
snapshot = normalized_snapcast_state()
```

失败后执行 best-effort rollback：

```text
恢复原 Group.SetClients
恢复 group name
恢复 stream
```

如果 Snapserver 本身状态已无法完整恢复：

```json
{
  "ok": false,
  "partialMutation": true,
  "error": "...",
  "state": ...
}
```

前端：

- 显示明确错误
- 强制 refresh
- 不显示普通“已更新”

### 7.4 测试

模拟：

```text
第一次 RPC 成功
第二次 RPC 失败
```

验证：

- rollback 被调用
- 返回状态不伪装成功
- 不留下 silent partial mutation

## 9. UI-02：721–900px 内容/iframe 可能被底栏遮挡

### 9.1 现状

`responsive.css` 在 `<=900px`：

```css
.sidebar {
  position: fixed;
  bottom: 0;
  height: 62px;
}
```

但 `device-console.css` 全局又有：

```css
.device-shell {
  padding-bottom: 0;
}
```

只在 `<=720px` 才重新补：

```css
padding-bottom: calc(62px + env(safe-area-inset-bottom));
```

播放器：

```css
.player-mode .workspace {
  height: 100vh;
}
```

只在 `<=700px` 才减掉底栏高度。

### 9.2 影响

在 721–900px：

- 普通页面最后内容可能被 fixed bottom nav 遮住。
- myMPD iframe 底部可能被遮住约 62px。
- 平板横屏/窄窗口最容易出现。

### 9.3 修复原则

统一一个导航模式 breakpoint：

```text
Desktop: >900
Mobile/Tablet: <=900
```

在 `<=900px` 同时处理：

```text
bottom nav
3-column layout
workspace bottom padding
safe-area
player viewport height
toast bottom
```

建议：

```css
@media (max-width: 900px) {
  .device-shell {
    padding-bottom: calc(62px + env(safe-area-inset-bottom));
  }

  .player-mode .workspace {
    height: calc(100dvh - 62px - env(safe-area-inset-bottom));
  }
}
```

优先使用：

```text
100dvh
```

而不是移动端固定 `100vh`。

```text

  ↓
```

目标：

> myMPD 保持独立升级能力，Snap/Room 外壳不与 myMPD 内部 UI 竞争。
