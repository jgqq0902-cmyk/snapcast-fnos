我已经对当前 `main` 分支做了一轮以**安全性、部署架构、FNOS 适配、稳定性和可维护性**为重点的静态审查。项目整体完成度其实不错：Snapserver、AirPlay、DLNA/MPD、本地曲库和统一 Web 控制台已经形成比较清晰的一体化架构，且代码里对路径、MPD 指令和前端输出做了不少防护。([GitHub][1])

## 一、审查结论

目前**没有发现需要判为 Critical 的直接远程代码执行、任意文件写入、明显命令注入或目录穿越漏洞**。

但我认为有 **2 个高优先级安全问题 + 4 个中优先级问题**。其中最应该先处理的，不是播放器业务代码，而是：

> **“局域网控制面完全信任 + Snapcast 原生控制面暴露 + 部分核心服务以 root 身份运行”这一组合。**

在完全可信的家庭独立 VLAN 中问题尚可接受；但如果 FNOS 所在网络同时存在 IoT、访客 Wi-Fi、办公电脑，或者未来通过反代、DDNS、VPN 之外的方式开放 Web 页面，则当前配置不建议直接使用。

### 审计问题表

| 编号       | 等级     | 问题                                               | 判断       |
| -------- | ------ | ------------------------------------------------ | -------- |
| **R-01** | **高**  | Web 控制 API 无认证                                   | 应优先修复    |
| **R-02** | **高**  | Snapcast 原生 JSON-RPC/TCP 控制面仍对 LAN 开放            | 应优先修复    |
| **R-03** | **中高** | Web Control、MPD 实际以 root 运行，MPD 还使用 `umask=0000` | 应修复      |
| **R-04** | **中**  | FNOS 网络地址被写死，修改 compose 后 DLNA 可能失效              | 功能性缺陷    |
| **R-05** | **中**  | Docker 基础镜像 `latest` + Alpine `edge`，构建不可复现      | 运维风险     |
| **R-06** | **中**  | 部分 HTTP API 可以触发大范围磁盘扫描/无上限文件读取                  | DoS/性能风险 |
| **R-07** | **低**  | 单元测试不错，但缺 HTTP、安全、容器集成测试                         | 工程完善项    |

## R-01：Web 控制台没有身份认证 —— 高

这是当前最明确的问题。

控制程序直接：

```python
ThreadingHTTPServer(("0.0.0.0", CONTROL_PORT), Handler)
```

也就是监听容器所有网络接口。POST API 可以执行播放器控制、修改曲库目录、Snapcast 音量、延迟、切换音源以及全组切流等操作，而 Handler 前面没有任何登录、Token 或 Authorization 判断。([GitHub][2])

所以同一 LAN 中只要知道：

```text
http://192.168.2.125:1781
```

就可以控制整个播放系统。

这虽然不等同于“已经能够执行任意系统命令”，但它已经是一个**未授权管理接口**。

建议设计成默认 fail-closed，例如增加：

```text
CONTROL_AUTH_ENABLED=true
CONTROL_PASSWORD=...
```

首次部署生成随机密码；登录后使用 HttpOnly + SameSite=Strict session cookie。若希望保持家庭设备使用方便，也可以提供：

```text
CONTROL_AUTH_ENABLED=false
```

作为用户明确选择的“可信家庭 LAN 模式”，而不要默认无认证。

## R-02：只保护 1781 还不够，Snapcast 自带控制面可以绕过去 —— 高

这个问题甚至比 R-01 更容易在后续修改时被遗漏。

当前 `snapserver.conf` 中：

```ini
[http]
#enabled = true
#bind_to_address = ::
#port = 1780

[tcp-control]
#enabled = true
#bind_to_address = ::
#port = 1705
```

这些注释实际对应 Snapcast 默认配置，HTTP 控制和 TCP JSON-RPC 控制默认启用，并且不是限制在 localhost。([GitHub][3])

Snapcast 官方本身就允许通过 TCP、HTTP/WebSocket JSON-RPC 修改音量、静音、分组和音源等状态。([GitHub][4])

也就是说，即便将来给你自己的 `1781` Web 页面加了密码：

```text
用户 → 1781 → 有认证
```

攻击者仍可能：

```text
用户/设备 → 1780 JSON-RPC → Snapserver
用户/设备 → 1705 TCP JSON-RPC → Snapserver
```

从而绕过你的认证。

这个项目更合理的网络边界应该是：

```text
LAN
 │
 ├── 1704  Snapcast audio streaming   ← 保留 LAN
 │
 ├── 1781  自己的 Web 控制台          ← 有认证
 │
 ├── AirPlay / DLNA                   ← 保留 LAN
 │
 │
 └─X─ 1780 / 1705 Snapcast control
             ↓
          localhost only
```

例如明确设置：

```ini
[http]
enabled = true
bind_to_address = 127.0.0.1
port = 1780

[tcp-control]
enabled = true
bind_to_address = 127.0.0.1
port = 1705
```

你的 control 服务已经配置为：

```text
SNAPSERVER_RPC_URL=http://127.0.0.1:1780/jsonrpc
```

所以这么改基本正好符合现有架构，不需要修改 Web 控制程序。([GitHub][5])

**1704 音频流端口继续开放即可。**

## R-03：已经做了一半的降权，但 Control 和 MPD 漏掉了 —— 中高

这一点比较可惜，因为项目显然已经有安全意识。

Supervisor 中：

```ini
snapserver → user=snapcast
dbus       → user=snapcast
avahi      → user=snapcast
shairport  → user=snapcast
upmpdcli   → user=snapcast
```

这些都很好。

但是：

```ini
[program:mpd]
...
umask=0000
```

没有 `user=snapcast`。

Control 同样：

```ini
[program:control]
command=/usr/bin/python3 /app/control/app.py
```

也没有 `user=`。

而 supervisord 自身是：

```ini
[supervisord]
user=root
```

所以 **MPD 和 Web Control 最终继承 root 身份运行**。([GitHub][5])

Docker Compose 本身同样使用：

```yaml
user: "0:0"
```

因此这不是仅仅显示上的问题。

值得肯定的是 `/vol1/1000` 音乐目录是只读挂载，没有 docker.sock，也没有看到 privileged 模式，所以宿主机攻击面已经比很多家庭 Docker 项目小不少。([GitHub][6])

建议至少改为：

```ini
[program:mpd]
user=snapcast
umask=0022

[program:control]
user=snapcast
```

然后仅让 entrypoint 在启动阶段使用 root 创建目录/chown：

```text
/app/data
/app/config
/app/certs
```

之后所有长期网络服务都以 `snapcast` 身份运行。

这样即使未来 Control、mutagen、MPD 或某个解析器出现漏洞，其影响范围也会明显缩小。

## R-04：网络地址存在“双重配置”，这是实际部署隐患 —— 中

Compose 中 FNOS 地址被配置为：

```text
192.168.2.125
```

但 `upmpdcli.conf` 又单独写死：

```ini
upnpip = 192.168.2.125
```

([GitHub][7])

README 告诉用户部署到其他网络时修改 compose 的：

```text
subnet
gateway
parent
IPv4 address
```

但如果用户把容器改成：

```text
192.168.1.50
```

而忘记修改 `upmpdcli.conf`，DLNA 部分仍认为自己的地址是：

```text
192.168.2.125
```

就很容易出现“Snapcast 正常、Web 正常，但手机 DLNA 找不到或控制异常”的疑难问题。

建议彻底消除静态配置：

```yaml
environment:
  GATEWAY_IP: 192.168.2.125
```

然后 entrypoint 根据 `${GATEWAY_IP}` 生成 upmpdcli 配置。

甚至可以启动时直接获取容器当前 IPv4，从而做到：

```text
docker-compose.yml
      ↓
唯一网络配置源
      ↓
entrypoint
      ↓
upmpdcli
```

这对 FNOS 项目很重要。

## R-05：Docker 构建目前不可复现 —— 中

Dockerfile 第一行：

```dockerfile
FROM ghcr.io/firefrei/snapcast/server:latest
```

同时安装：

```dockerfile
--repository=https://dl-cdn.alpinelinux.org/alpine/edge/main
--repository=https://dl-cdn.alpinelinux.org/alpine/edge/community
```

而 `mpd`、`py3-mutagen`、`upmpdcli` 都没有锁版本。([GitHub][8])

因此完全相同的仓库：

```text
今天 docker compose build
```

和：

```text
三个月后 docker compose build
```

可能得到不同的 Snapcast、MPD、upmpdcli 和依赖组合。

对于你的这种**长期运行的 NAS 音频基础服务**，这是比较大的运维隐患，因为一次普通 rebuild 都可能突然破坏 AirPlay/DLNA/Snapcast 兼容性。

建议至少锁定基础镜像版本，例如：

```dockerfile
FROM ghcr.io/firefrei/snapcast/server:<明确版本>
```

正式 release 最好进一步锁 digest：

```dockerfile
FROM ...@sha256:...
```

Alpine edge 如果确实因为 upmpdcli 新版本必须使用，可以保留，但最好记录当前成功构建的软件版本并增加构建测试。

## R-06：大曲库情况下存在两个资源消耗点 —— 中

### 1. 每次请求扫描整个 `/media`

`server_playlist_files()` 当前直接：

```python
root.rglob("*")
```

然后遍历整个音乐目录寻找 `.m3u/.m3u8/.pls`，找到 500 个才停止。([GitHub][2])

问题在于：

```text
“最多返回 500 个”
≠
“最多扫描 500 个文件”
```

如果 `/vol1/1000` 中有：

```text
30 万首歌曲
20 万张图片
几十万个其他文件
但只有 5 个 m3u
```

一次 API 请求可能需要遍历几十万个目录项。

结合 R-01 的未认证接口，同一 LAN 设备可以反复触发磁盘扫描。

更合适的是：

```text
第一次扫描
   ↓
缓存 playlist index
   ↓
TTL 30~60 秒
```

或者仅扫描指定 playlist 目录。

### 2. 封面和歌词没有文件大小上限

歌单导入反而做得很好：

```python
if len(raw) > 1024 * 1024:
    raise ControlError(...)
```

但封面：

```python
data = candidate.read_bytes()
```

以及歌词：

```python
raw = candidate.read_bytes()
```

没有类似限制。([GitHub][2])

普通音乐库当然不会有问题，但一个异常的：

```text
folder.jpg = 2GB
```

就可能让 Python 一次性尝试读入 2GB。

建议：

```text
封面：20 MB 左右上限
歌词：2~5 MB 上限
```

已经足够宽松。

特别是已经有：


再增加一个真正启动 Docker 镜像的 smoke test，整个项目可靠性会明显提升。

# 值得保留的设计

这轮审查中，下面几个地方我建议**不要因为安全整改而重写**。

库路径处理使用 `resolve()` 后再判断目标必须位于 `LIBRARY_ROOT` 之下，能正确阻止 `../` 越界；服务器歌单导入也再次做了同样的目录边界检查。([GitHub][2])

MPD 字符串不是简单拼接裸参数，`mpd_escape()` 会拒绝 CR/LF/NUL，并对引号和反斜杠进行处理，测试中还专门覆盖了 `"song\nstop"` 这种典型命令注入。([GitHub][9])

Web 静态文件使用 `resolve()` 后检查必须位于 `STATIC_DIR` 内；HTTP JSON body 有 Content-Type 和约 1.1 MB 的长度限制；响应还设置了 CSP、`X-Frame-Options: DENY`、`nosniff`、`Referrer-Policy`。这些都是值得保留的。([GitHub][2])

前端输出也不是大量裸 `innerHTML`。歌曲名、艺人、歌词、客户端名称等基本经过 `esc()`；封面 URI 又先经过 `encodeURIComponent()` 再组成内部 `/api/player/art` 地址，目前没有看到明显 XSS 链。([GitHub][10])

# 我建议的修复优先级

如果准备继续完善这个项目，我会按下面顺序处理：

1. **P0：R-02** —— 把 Snapcast `1780/1705` 限制到 `127.0.0.1`，改动最小、收益最大。
2. **P0：R-01** —— 给 1781 Web Control 增加可配置认证。
3. **P0：R-03** —— `control`、`mpd` 改成 `user=snapcast`，取消 `umask=0000`。
4. **P1：R-04** —— 网络 IP 单一配置源，不再把 `192.168.2.125` 写死两次。
5. **P1：R-06** —— 歌单索引缓存 + 封面/歌词尺寸限制。
6. **P1：R-05** —— 固定 Docker 镜像和关键依赖版本。
7. **P2：R-07** —— 增加 HTTP、安全边界和 Docker 集成测试。

**综合评价：当前项目业务架构可以继续沿用，不需要推倒重构。** 它已经越过了“临时 Docker 脚本”的阶段，核心代码的输入安全也做得比较认真；现在最需要做的是把它从“默认信任整个家庭局域网的个人工具”，收口成一个**有明确安全边界、可长期在 FNOS 上运行的家庭音频网关**。

如果按上一轮 `daer` 项目的方式继续，我下一步可以直接针对这个仓库做一轮**逐文件审计 + 给出 R-01～R-07 的具体代码修改方案/patch 级建议**，包括 `docker-compose.yml`、`snapserver.conf`、`supervisord.conf`、`app.py` 和测试应该分别怎么改。
